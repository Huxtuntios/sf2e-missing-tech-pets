# Подготовка и выпуск через GitHub Desktop

Кандидат: **1.7.0**, предполагаемый тег после одобрения: **v1.7.0**.
Репозиторий: https://github.com/Huxtuntios/sf2e-missing-tech-pets
Рабочая ветка: `feature/tech-pets-1.7.0`. Не вносите эти изменения прямо в `main`.

## Проверка кандидата

1. В GitHub Desktop выберите рабочую ветку и проверьте diff. Исходный ZIP не содержит `.git`, зависимостей, локальных настроек и кэшей; установочный ZIP — отдельный файл.
2. Версии должны совпадать в `module.json`, `package.json` и обоих полях `package-lock.json` (`version`, `packages[""].version`). Изменение версии оформляется отдельным коммитом.
3. Проверьте `CHANGELOG.md`, `README.md`, `README.ru.md`, `docs/RELEASE-NOTES.md` и `docs/AUDIT-1.7.0.md`. Не повышайте `verified` по одному манифесту или mock-тестам.
4. Запустите статические проверки, тесты и проверку архивов. Установите сборку в отдельные тестовые миры SF2e/PF2e и выполните живой чек-лист аудита. Сохраните результаты с точными версиями и ролями клиентов.
5. Не заменяйте установленную копию 0.16.2 и не меняйте действующие миры ради проверки кандидата.

## Локальная сборка

Нужны Node.js 22+, Python 3 и зависимости проекта. Используйте реальные команды этого проекта, а не команды другого шаблона:

```sh
npm ci
npm run build:packs
npm run check
npm test
npm run package
npm run verify:release -- dist v1.7.0
```

Для браузерной fixture:

```sh
node tools/serve-ui-fixtures.mjs
```

Откройте адрес, выведенный сервером, и `tests/fixtures/browser.html`. Это mock-документы Foundry, не проверка нативных листов или живой совместимости. Скриншоты и DOM-проверки не заменяют чек-лист тестового мира.

`dist/` содержит:

- `module.json` — манифест;
- `module.zip` — установочный архив с `module.json` в корне;
- `SHA256SUMS.txt` — контрольные суммы;
- `RELEASE-NOTES.md` — примечания к выпуску.

Для ручной установки распакуйте `module.zip` в `Data/modules/sf2e-missing-tech-pets/`. Не используйте автоматические GitHub **Source code** ZIP/TAR как установочный пакет: это другой артефакт.

## Коммиты и Pull Request

1. Сделайте логические коммиты проверенных изменений в рабочей ветке; номер версии — отдельным `chore`.
2. Push этой ветки и открытый PR в `main` не означают выпуск. Просмотрите CI и приложенные артефакты, но не выдавайте зелёный mock-тест за живую проверку.
3. Оставьте PR открытым для решения сопровождающего. **Merge, тег и Release не выполняются автоматически.**
4. После одобрения сопровождающий отдельно решает вопрос слияния и публикации.

## Публикация после одобрения

Эти действия выполняет сопровождающий только после нужных проверок. GitHub Desktop не публикует Release самостоятельно.

1. После одобренного слияния откройте **Releases → Draft a new release**, выберите `v1.7.0` и утверждённый commit.
2. Вставьте содержимое `docs/RELEASE-NOTES.md`, обновив статус кандидата и добавив реальные результаты живых проверок.
3. Для обычного выпуска выберите **Set as the latest release**, не draft/prerelease.
4. Публикация запускает существующий workflow **Release**; он проверяет совпадение тега/версии, собирает и прикрепляет `module.json`, `module.zip`, `SHA256SUMS.txt`, затем проверяет опубликованные assets и latest endpoint.
5. При **Immutable release** прикрепите проверенные assets к черновику до публикации: дополнение неизменяемого релиза после публикации невозможно.

Постоянный адрес не меняется:

```text
https://github.com/Huxtuntios/sf2e-missing-tech-pets/releases/latest/download/module.json
```

После публикации конкретной версии:

```text
https://github.com/Huxtuntios/sf2e-missing-tech-pets/releases/download/v1.7.0/module.json
```

До публикации этих assets версия недоступна по ссылке тега. Коммит, push и PR не обновляют Foundry автоматически.

## Ошибки публикации

- **Тег не совпадает с версией:** сверяйте тег с четырьмя полями версий и `download`; опубликованный номер не переиспользуется.
- **403 при загрузке assets:** проверьте ограничения GitHub Actions на запись `contents`; не обходите проверки workflow.
- **Нет workflow:** проверьте наличие `.github/workflows` в коммите и разрешение Actions.
- **Foundry не предлагает обновление:** проверьте версию именно публичного latest-манифеста, совпадение ZIP и статуса Latest. Установка с tag-specific manifest требует осознанной переустановки по постоянному адресу.
- **Красный Check public latest manifest:** выясните причину (старый latest, HTTP-ошибка, несовпадение версии/ZIP). Нельзя считать такую публикацию успешной.
